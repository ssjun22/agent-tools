# Project Context Init

## 목적

현재 프로젝트 레포에 `.claude/context/` 구조를 초기화한다.
브라운필드(기존 코드가 있는) 프로젝트에서는 코드베이스 스캔과 사용자 인터뷰를 통해 핵심 context를 채워준다.

## 브라운필드 초기화의 범위

프로젝트 초기부터 점진적으로 쌓아온 context 전체를 한 번의 초기화로 재구성할 수는 없다. 브라운필드 초기화는 **AI가 매 세션에서 프로젝트를 파악하기 위한 핵심 골격**을 만드는 것이 목표다. 세부 도메인 지식이나 완료 이력 등은 이후 작업하면서 점진적으로 채워나간다.

### 초기화로 채울 수 있는 것 vs 점진적으로 쌓는 것

| 구분 | 섹션 | 소스 |
|------|------|------|
| **초기 생성** | 목적 | 인터뷰 |
| **초기 생성** | 시스템 구성 | 스캔 + 인터뷰 확인 |
| **초기 생성** | 도메인 용어 | 인터뷰 |
| **초기 생성** | 아키텍처 결정 (무엇 + 왜) | 스캔 + 인터뷰 |
| **초기 생성** | 핵심 변경 이력 | 인터뷰 (현재 코드를 이해하는 데 필수적인 과거 변경만) |
| **초기 생성** | 현재 업무 상태 | 인터뷰 |
| **초기 생성** | 보류/제외 | 인터뷰 (있는 경우만) |
| **초기 생성** | 외부 링크 | 인터뷰 (있는 경우만) |
| 스캔 기반 | 데이터, 입출력, 요구사항 목록 | 스캔 (정확도 한계 있음) |
| 점진 축적 | Breaking Changes 상세 이력 | 이후 발생 시 기록 |
| 점진 축적 | 도메인 세분화, 역할 상세, 그룹 분류 | 작업하면서 추가 |
| 점진 축적 | 완료 업무 이력 | 작업하면서 누적 |

## 실행 절차

### Phase 0: 사전 확인

1. `.claude/context/` 디렉토리 존재 여부 확인
   - 이미 있으면 덮어쓰기 전에 사용자에게 확인
2. 프로젝트 유형 판단
   - 코드가 이미 있는가? (소스 파일, 의존성 파일, git 이력 존재 여부)
   - **그린필드** (코드 없음) → Phase 3으로 건너뛰어 빈 템플릿만 생성
   - **브라운필드** (코드 있음) → Phase 1부터 진행

### Phase 1: 코드베이스 스캔 (자동)

사용자 개입 없이 코드에서 파악 가능한 정보를 수집한다.

**스캔 대상:**

| 수집 항목 | 탐색 위치 |
|-----------|-----------|
| 기술 스택, 의존성 | `package.json`, `requirements.txt`, `pyproject.toml`, `go.mod` 등 |
| 디렉토리 구조 | 최상위 + 1~2레벨 하위 디렉토리 |
| API 엔드포인트 | 라우터/컨트롤러 파일 |
| 데이터 스키마 | ORM 모델, Pydantic 모델, migration 파일, 타입 정의 |
| 설정 | 환경변수, config 파일 |
| 기존 문서 | README, CLAUDE.md, openspec/ |

**스캔 결과물:** 내부 메모로 보관. Phase 2 질문 생성과 Phase 3 파일 작성에 사용.

### Phase 2: 인터뷰 (3라운드)

코드에서 파악할 수 없는 핵심 맥락을 질문한다.

**원칙:**
- 코드에서 파악한 내용은 묻지 않고, 초안을 보여주며 확인받는다
- 답변이 짧아도 되도록 질문을 구체적으로 만든다
- "모름" 또는 "나중에"라고 답하면 해당 섹션을 비워둔다

#### 라운드 1: 프로젝트 핵심

스캔 결과 초안을 보여준 뒤 질문한다.

```
코드를 스캔한 결과입니다:
- 기술 스택: [스캔 결과]
- 구성 요소: [디렉토리별 역할 추정]
- API: [발견된 엔드포인트 요약]

위 내용에서 수정할 부분이 있으면 알려주세요.

질문:
1. 이 프로젝트의 목적은 무엇인가요? (1~3문장)
2. 이 프로젝트에서만 쓰는 용어가 있나요? (없으면 "없음")
3. 누가, 어떤 데이터를 대상으로 사용하나요?
4. 이 시스템의 주요 사용 흐름을 알려주세요.
   (예: "사용자가 X를 입력하면 → Y가 처리되고 → Z가 저장된다")
```

#### 라운드 2: 아키텍처와 핵심 변경

```
코드에서 파악한 주요 기술 선택:
- [스캔에서 발견한 기술 결정 목록]

5. 위 기술 선택 중 특별한 이유가 있는 게 있나요? (없으면 생략)
6. 이 프로젝트에서 큰 구조 변경이나 방향 전환이 있었나요?
   현재 코드를 이해하려면 꼭 알아야 할 과거 결정이 있으면 알려주세요.
   (예: "원래 A 방식이었는데 B로 바꿨다", "X를 쓰다가 Y로 전환했다")
7. 이 프로젝트에서 건드리면 안 되는 것이나, 알아야 할 함정이 있나요?
   (예: "이 설정을 바꾸면 장애 발생", "이 파일은 자동 생성이라 수정 금지")
8. 의도적으로 보류하거나 제외한 기능이 있나요?
```

#### 라운드 3: 현재 상태

```
9. 현재 진행 중인 작업이 있나요?
10. 예정된 작업이 있나요?
11. 관련 외부 링크가 있나요? (문서, 대시보드, 이슈 트래커 등)
```

### Phase 3: 파일 생성

스캔 결과 + 인터뷰 답변을 합쳐 context 파일을 생성한다.

**생성 파일:**
- `.claude/context/index.md` — `references/index-template.md` 기반
- `.claude/context/project.md` — `references/project-template.md` 기반
- `.claude/context/status.md` — `references/status-template.md` 기반
- `.claude/context/refs/` — 빈 디렉토리

**project.md 작성 기준:**

| 섹션 | 작성 방식 |
|------|-----------|
| 목적 | 인터뷰 R1-Q1 |
| Breaking Changes | 인터뷰 R2-Q6 핵심 변경 → 있으면 기록, 없으면 빈 테이블 |
| 시스템 구성 | 스캔 초안 + 인터뷰 R1 수정 반영 |
| 데이터 | 스캔 기반 (있는 경우만) |
| 워크플로우 | 인터뷰 R1-Q4 |
| 도메인 용어 | 인터뷰 R1-Q2 (있는 경우만) |
| 공통 입출력 | 스캔 기반 + 인터뷰 R1-Q3 대상 범위 |
| 전체 요구사항 | 스캔 기반 엔드포인트/기능 목록 |
| 보류/제외 | 인터뷰 R2-Q8 (있는 경우만, 없으면 빈 테이블) |
| 아키텍처 결정 | 스캔(무엇) + 인터뷰 R2-Q5(왜) + R2-Q6(핵심 변경 이유) + R2-Q7(함정/주의사항) |
| 외부 링크 | 인터뷰 R3-Q11 (있는 경우만) |

**status.md 작성 기준:**
- 진행 중/예정: 인터뷰 R3 답변 반영
- 완료: 비워둠 (이후 누적)

### Phase 4: 안내

```
.claude/context/ 초기화 완료.

채워진 섹션:
- [작성된 섹션 목록]

빈 섹션 (작업하면서 점진적으로 채워나가세요):
- [비어있는 섹션 목록]

점진적으로 쌓이는 항목:
- Breaking Changes: 앞으로 발생하는 변경 기록
- 도메인 세분화: 작업하면서 역할/분류 상세화
- 완료 이력: 작업 완료 시 status.md에 누적

참조 문서 추가 시:
- refs/ 에 파일 생성 후 index.md에 등록

hooks 미설치 시:
- agent-tools/plugins/project-context/hooks/load-context → .claude/hooks/ 복사
- agent-tools/plugins/project-context/settings.json → .claude/settings.local.json 복사
- chmod +x .claude/hooks/load-context
```
