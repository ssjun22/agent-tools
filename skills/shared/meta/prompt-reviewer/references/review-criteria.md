# Review Criteria

에이전트 시스템 프롬프트 리뷰 기준. Phase 1(구조 검사)과 Phase 2(내용 리뷰)로 구성된다.

---

## Phase 1: 구조 검사

에이전트 시스템 프롬프트가 갖춰야 할 필수 요소의 존재 여부를 검사한다.
누락된 요소가 하나라도 있으면 해당 요소를 지적하고 Phase 2로 넘어가지 않는다.

### 1. 역할/목적 정의

에이전트가 무엇이고 왜 존재하는지 명시되어 있는가.

**감지 기준:**
- 에이전트의 정체성(무엇인가)이 선언되어 있는가
- 에이전트의 목적(왜 존재하는가)이 설명되어 있는가
- 역할의 범위(무엇을 담당하고 무엇을 담당하지 않는가)가 식별 가능한가

### 2. 지시사항

에이전트가 수행해야 할 구체적 행동 지시가 존재하는가.

**감지 기준:**
- 에이전트가 실행해야 할 동작이 하나 이상 명시되어 있는가
- 지시가 행동 동사(action verb)로 시작하는가 ("~을 분석한다", "~을 생성한다")
- 지시가 실행 가능한 수준으로 구체적인가 (추상적인 "잘 처리한다"가 아닌)

### 3. 제약/경계

에이전트가 하지 말아야 할 것, 범위 밖의 행동이 정의되어 있는가.

**감지 기준:**
- 금지 행동 또는 범위 밖 영역이 명시되어 있는가
- 에이전트의 판단 범위가 어디까지인지 식별 가능한가

### 4. 출력 형식

에이전트의 응답 형태가 명시되어 있는가.

**감지 기준:**
- 출력 포맷(텍스트, JSON, Markdown 등)이 정의되어 있는가
- 출력에 포함해야 할 필드/항목이 명시되어 있는가

### 5. 불확실성 정책

에이전트가 모르거나 애매한 상황에서 어떻게 행동해야 하는지 정의되어 있는가.

**감지 기준:**
- 정보가 부족하거나 판단이 불확실할 때의 행동이 정의되어 있는가
- 범위 밖 요청을 받았을 때의 대응이 정의되어 있는가

---

## Phase 2: 내용 리뷰

구조가 갖춰진 프롬프트의 내용 품질을 평가한다. 해당되는 이슈를 모두 보고한다.

### 1. 명확성/구체성

모호하지 않고 실행 가능한 지시인가.

**왜 문제인가:**
모호한 지시는 에이전트가 의도와 다르게 해석하거나, 불필요한 추론에 토큰을 낭비하게 만든다. 상충하는 지시는 에이전트의 행동을 예측 불가능하게 만든다.

**감지 기준:**
- 같은 상황에 대해 상충하는 지시가 존재하는가
- "적절하게", "필요에 따라", "가능하면" 같은 해석의 여지가 큰 표현이 사용되었는가
- 암묵적 가정(명시되지 않은 전제)에 의존하는 지시가 있는가
- 정량화 가능한 기준이 정성적 표현으로 대체되어 있는가 ("짧게" 대신 "3문장 이내")

**개선 예시:**
- before: "사용자 요청을 적절하게 처리한다"
- after: "사용자 요청을 분석하여 1) 요청 유형을 분류하고 2) 해당 유형의 처리 절차를 실행한다"

### 2. 지시사항 구조화

논리적 순서로 구성되고, 섹션이 적절히 분리되어 있는가.

**왜 문제인가:**
구조화되지 않은 프롬프트는 에이전트가 지시를 누락하거나 우선순위를 잘못 판단하게 만든다. 관련 없는 지시가 혼재되면 맥락 파악이 어려워진다.

**감지 기준:**
- 관련 없는 지시가 하나의 섹션에 혼재되어 있는가
- 지시의 논리적 순서가 실행 순서와 일치하는가
- 구분자(Markdown 헤딩, XML 태그 등)가 일관적으로 사용되었는가
- 하나의 섹션에 과도하게 많은 지시가 밀집되어 있는가 (지시 과부하)

**개선 예시:**
- before: 역할, 출력 형식, 제약, 역할 보충 설명이 뒤섞인 단일 블록
- after: `## Role` → `## Instructions` → `## Constraints` → `## Output Format` 으로 분리

### 3. 제약 설계 품질

제약이 과하지도 부족하지도 않으며, 의도한 경계를 정확히 표현하는가.

**왜 문제인가:**
과도한 제약은 에이전트의 유용한 행동까지 억제한다. 광범위한 부정문은 의도하지 않은 기능 거부를 유발한다. 반대로 제약이 부족하면 에이전트가 범위를 벗어난 행동을 한다.

**감지 기준:**
- 범위가 넓은 부정문("추론하지 마", "가정하지 마")이 구체적 범위 없이 사용되었는가
- 동일한 행동을 여러 곳에서 반복적으로 금지하고 있는가 (과잉 강조)
- 제약이 지시사항과 모순되는가 (예: "창의적으로 작성하라" + "예시 외의 표현을 사용하지 마")
- 제약의 경계가 불명확하여 에이전트가 판단할 수 없는가

**개선 예시:**
- before: "외부 정보를 추론하지 마"
- after: "제공된 텍스트에 기반해서만 답변한다. 텍스트에 없는 외부 지식은 도입하지 않는다"

### 4. 자율성 보정

에이전트가 언제 스스로 진행하고, 언제 멈추고, 언제 사용자에게 확인해야 하는지 정의되어 있는가.

**왜 문제인가:**
자율성이 과하면 위험한 행동을 사용자 확인 없이 실행한다. 자율성이 부족하면 매 단계마다 확인을 요청하여 비효율적이다.

**감지 기준:**
- 에이전트가 독립적으로 진행해도 되는 행동과 확인이 필요한 행동이 구분되어 있는가
- 정지 조건(언제 작업을 멈추는가)이 정의되어 있는가
- 가역적 행동과 비가역적 행동에 대한 구분이 있는가
- 태스크 완료 기준이 명시되어 있는가

**개선 예시:**
- before: "사용자의 요청을 처리한다"
- after: "읽기 작업은 즉시 실행한다. 파일 수정/삭제는 실행 전 사용자 확인을 받는다. 요청이 모호하면 명확화를 요청한다"

### 5. 도구 통합

도구 사용에 대한 안내가 명확하고, 도구 간 역할이 구분되어 있는가.

**왜 문제인가:**
도구 설명이 불명확하면 에이전트가 잘못된 도구를 선택하거나 도구를 사용하지 않는다. 도구 간 역할이 중복되면 선택 오류가 발생한다.

**감지 기준:**
- 도구를 언제 사용해야 하는지(트리거 조건)가 명시되어 있는가
- 유사한 도구 간 역할 차이가 설명되어 있는가
- 도구 사용 결과를 어떻게 처리해야 하는지 안내되어 있는가
- 도구가 없는 프롬프트에서 이 항목은 N/A로 처리한다

**개선 예시:**
- before: "필요하면 검색 도구를 사용한다"
- after: "사용자가 최신 정보를 요청하거나 학습 데이터로 답변할 수 없는 경우 검색 도구를 사용한다. 검색 결과는 출처와 함께 인용한다"

### 6. 추론/계획

복잡한 작업에 대해 단계적 추론이나 계획 수립이 안내되어 있는가.

**왜 문제인가:**
복잡한 작업을 한 번에 처리하도록 지시하면 에이전트가 중간 단계를 누락하거나 논리적 비약을 범한다. 단계별 분해가 없으면 결과의 품질과 일관성이 저하된다.

**감지 기준:**
- 복잡한 작업(다단계 분석, 의사결정 등)에 대해 단계별 절차가 제시되어 있는가
- 각 단계의 입력과 출력이 명확한가
- 단계 간 의존 관계가 식별 가능한가
- 단순한 작업에 불필요한 단계를 강제하고 있지는 않은가

**개선 예시:**
- before: "코드를 리뷰하고 개선점을 제안한다"
- after: "1) 코드를 읽고 전체 구조를 파악한다 2) 버그, 보안 취약점, 성능 이슈를 식별한다 3) 각 이슈에 대해 원인과 개선 방안을 제시한다"

### 7. 예시 활용

적절한 예시(few-shot)가 포함되어 에이전트의 이해를 돕고 있는가.

**왜 문제인가:**
예시 없이 추상적 지시만 있으면 에이전트가 의도와 다른 형태로 출력한다. 반면 예시가 편향되면 에이전트가 예시 패턴만 모방하여 다양한 입력에 대응하지 못한다.

**감지 기준:**
- 출력 형식이 복잡하거나 비자명한 경우 예시가 포함되어 있는가
- 예시가 다양한 케이스(일반, 엣지)를 포함하는가
- 예시가 실제 사용 상황을 반영하는가
- 예시가 과도하게 많아 프롬프트를 비대하게 만들지 않는가 (2-5개 권장)

**개선 예시:**
- before: "다음 형식으로 출력한다: 이슈명, 설명, 제안"
- after: 위 형식 설명 + 실제 입력/출력 쌍 2-3개를 `<example>` 태그로 제공
