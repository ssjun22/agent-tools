# PR Review Critical Rules

PR 리뷰 작성 시 반드시 따라야 할 규칙입니다.

## DO

✅ **실제 심각도에 따라 분류하기**
- 모든 것을 Critical로 표시하지 말 것
- 각 이슈의 실제 영향도를 평가하여 적절한 카테고리 선택
- Critical: 버그, 보안 이슈, 데이터 손실
- Important: 아키텍처 문제, 테스트 누락
- Minor: 코드 스타일, 문서화

✅ **구체적으로 작성하기**
- 파일:라인 번호를 정확히 명시 (`src/components/Header.tsx:45-50`)
- "개선이 필요합니다" 같은 모호한 표현 지양
- 구체적인 코드 조각과 함께 설명

✅ **WHY를 설명하기**
- 왜 이것이 문제인지 이유 설명
- 비즈니스/기술적 영향 명시
- "이렇게 하면 X 문제가 발생할 수 있습니다" 형식

✅ **강점 인정하기**
- 잘된 점을 명시적으로 언급
- 균형있는 피드백 제공
- 구체적인 칭찬 (파일:라인 포함)

✅ **명확한 결론 내리기**
- Ready to merge? 질문에 명확히 답변
- 1-2문장으로 기술적 근거 제시
- 머지 조건이 있다면 명시

✅ **코드 블록 포맷 준수**
- GitHub에서 올바르게 렌더링되도록 코드 블록 앞뒤에 **빈 줄** 추가
- 섹션 헤더 뒤에도 빈 줄 추가

## DON'T

❌ **검토하지 않고 "좋아 보입니다" 말하지 않기**
- 실제로 코드를 읽고 패턴을 확인한 후에만 승인
- 형식적인 리뷰 지양

❌ **사소한 것을 Critical로 표시하지 않기**
- 들여쓰기, 변수명 같은 nitpick은 Minor로
- 실제 버그나 보안 이슈만 Critical

❌ **리뷰하지 않은 코드에 피드백 주지 않기**
- 변경되지 않은 기존 코드에 대한 지적 지양
- PR 범위 내에서만 리뷰

❌ **모호하게 작성하지 않기**
- "에러 핸들링을 개선하세요" (X)
- "line 45에서 try-catch로 네트워크 에러를 처리하세요" (O)

❌ **명확한 결론 회피하지 않기**
- "좋아 보이지만..." 같은 애매한 표현 지양
- Yes/No/With fixes 중 하나 선택

## Priority Guidelines

### 우선순위별 작성 전략

**Critical/Important:**
- 상세한 설명 필수
- Before/After 코드 예시 제공
- 왜 문제인지, 어떤 리스크가 있는지 명확히 설명
- 개선 방법 구체적으로 제시

**Minor:**
- 간단한 설명
- 코드 예시는 선택적
- "선택적 개선 사항"으로 명시

## Review Structure Guidelines

1. **우선순위별 섹션 구성**: Critical → Important → Minor 순서로 작성
2. **구체적인 파일 경로**: 여러 파일이 해당되면 모두 나열 (라인 번호 포함)
3. **현재 코드**: 문제가 되는 코드 조각을 그대로 표시하여 컨텍스트 제공
4. **문제 설명**: "왜" 문제인지, "어떤 리스크"가 있는지 명확히 설명
5. **개선 방법**: 실제 코드 예시 제공 (복붙 가능하도록)
6. **긍정적 피드백**: 잘된 점도 반드시 포함하여 균형있는 리뷰 작성
