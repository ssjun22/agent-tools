# PR Review Output Format

PR 리뷰 코멘트는 다음 구조를 따릅니다.

## Overall Structure

```markdown
## PR #{number} 코드 리뷰

{전체 요약 - 1-2문장}

---

### ✅ Strengths

- ✨ {잘된 점 1 - 구체적으로 작성. 파일:라인 포함}
- ✨ {잘된 점 2}
- ✨ {잘된 점 3}

---

### Issues

#### ⚠️ Critical (Must Fix)

**1. {이슈 제목}**

**파일:**
- `path/to/file.ts:10-20`

**현재 코드:**

```{language}
{문제가 되는 코드 조각}
```

**문제:**

{왜 이것이 문제인지, 어떤 위험이 있는지 구체적으로 설명. 버그, 보안 이슈, 데이터 손실 위험, 기능 오작동 등}

**개선 방법:**

```{language}
{개선된 코드 예시}
```

---

#### 💡 Important (Should Fix)

**2. {이슈 제목}**

**파일:**
- `path/to/file.ts:30-40`

**현재 코드:**

```{language}
{문제가 되는 코드}
```

**문제:**

{아키텍처 문제, 누락된 기능, 부적절한 에러 핸들링, 테스트 부족 등}

**개선 방법:**

```{language}
{개선 코드}
```

---

#### 🔧 Minor (Nice to Have)

**3. {이슈 제목}**

{간단한 설명. 코드 스타일, 최적화 기회, 문서화 개선 등. 코드 예시는 선택적}

---

### Recommendations

{코드 품질, 아키텍처, 프로세스 개선을 위한 제안 사항}

---

### Assessment

**Ready to merge?** {Yes / No / With fixes}

**Reasoning:** {1-2문장으로 기술적 평가 작성}
```

## Issue Categories

| Category      | 의미           | 사용 기준                                                                   |
| ------------- | -------------- | --------------------------------------------------------------------------- |
| ⚠️ **Critical** | 반드시 수정    | 버그, 보안 이슈, 데이터 손실 위험, 기능 오작동 등 머지 전 필수 수정 사항 |
| 💡 **Important** | 수정 권장      | 아키텍처 문제, 누락된 기능, 부적절한 에러 핸들링, 테스트 부족 등         |
| 🔧 **Minor**    | 선택적 개선    | 코드 스타일, 최적화 기회, 문서화 개선 등 선택적으로 반영 가능한 사항     |

## Issue Template

각 이슈는 다음 정보를 포함해야 합니다:

- **파일:라인 참조** - 정확한 위치 명시
- **무엇이 잘못되었는지** - 현재 코드와 함께 설명
- **왜 중요한지** - 비즈니스/기술적 영향 설명
- **어떻게 고칠지** - 개선 방법 (명확하지 않은 경우에만)
