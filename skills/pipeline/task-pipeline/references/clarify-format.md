# task-pipeline clarify — 산출물 형식과 인터뷰 기법

clarify는 brainstorming 스킬의 핵심 3개 개념을 *내장*해 직접 수행한다. 스킬을 호출하는 게 아니라 그 기법을 메인이 적용한다.

## ⓪ 컨텍스트 문서 참조 (인터뷰 시작 전)

인터뷰 전에 프로젝트의 컨텍스트 문서를 흡수해, 질문과 정리가 프로젝트의 언어·기존 결정 위에서 출발하게 한다.

1. `docs/` 존재 확인 — 없으면 이 절차 전체를 조용히 skip (강제 생성하지 않는다)
2. `docs/` 파일 목록에서 *이번 작업과 관련된 문서만* 선별해 Read (전부 읽지 않는다 — 작업 내용 기준으로 판단)
3. 흡수한 내용을 인터뷰에 활용:
   - **용어**: 질문·정리에 문서의 도메인 용어를 그대로 사용
   - **기존 결정**: 사용자 요청이 문서화된 결정과 충돌하면 인터뷰 중 지적 (③ Socratic Challenge의 가정 후보로도 사용)
4. 읽은 문서가 있으면 산출물 `## 참조 컨텍스트 문서` 섹션에 기록 — 문서 경로 + 무엇을 반영했는지 한 줄씩. docs/ 부재로 읽은 문서가 없으면 이 섹션은 두지 않는다 (헤더명 고정 — context-doc-updater가 직접 참조).

## ① One question at a time

한 번에 한 질문만, 다지선다 우선.

여러 질문을 묶으면 사용자가 일부만 답하거나 답이 모호해진다. 다지선다는 답변 부담을 줄이고 응답을 명확하게 만든다.

### 좋은 예
> 이 작업의 통과 기준은 어느 쪽에 가깝나요?
> - A. 새 동작이 눈에 보이게 작동 (예: 버튼 클릭 시 목록 갱신)
> - B. 기존 동작이 깨지지 않으면 OK (회귀 없음)
> - C. 특정 입력에 대한 출력이 정확히 일치
> - D. 그 외 (직접 설명)

### 나쁜 예
> 이 작업의 목적은 뭐고, 어떤 파일을 건드릴 것 같고, 통과 기준은 무엇이고, 위험은 뭐죠?

답변에 깊이가 필요한 부분(예: 의도가 모호)은 개방형 질문으로 변경. 기본은 다지선다.

## ② Understanding Lock

### clarify 종료 조건

다음 4가지가 모두 명확해질 때까지 인터뷰를 계속한다. 미만에서 끝내면 explore/plan/evaluate가 흔들린다.

1. **목적** — 무엇을 왜 만드는가
2. **통과 기준** — 사용자가 관찰 가능한 동작으로, 무엇이 되면 통과인지가 명확한가. 자동 검증이 원천적으로 불가한 작업이면 *"verify 불가"* 임을 사용자와 합의
3. **non-goals** (= 산출물 '제외 범위') — 무엇을 하지 *않을* 것인가
4. **테스트 수준·대상** — 어떤 수준의 테스트로 무엇을 커버할지. *작성 여부*는 결정 대상이 아니다 (코드 변경이면 항상 작성). 아래 ④ 참고

넷 다 채워지면 Lock으로 넘어간다.

### Lock 진행

명시 정리를 보여주고 사용자 confirm을 받는다. 흐릿하게 explore로 넘어가면 잘못된 전제 위에 후속 단계가 쌓인다.

### 정리 형식 (= 산출물 `01-clarify.md` 본문)

Lock에서 사용자에게 보여주는 정리와 디스크 산출물은 아래 동일한 형식이다. **모든 문장은 사용자 인터뷰만으로 작성 가능해야 한다** — 코드·명령어·파일 경로 수준 정보는 explore/plan의 몫이다. 각 섹션은 하류 소비자와 1:1 대응한다 (요약→브랜치·evaluator·planner / 통과 기준→plan·evaluator / 제외 범위→planner Non-goals / 테스트 범위→explorer·planner / 미확정 사항→메인 explore 전후 질문 / 참조 컨텍스트 문서→context-doc-updater).

```markdown
## 요약
- 작업: <한 줄 — 브랜치 slug 원천, 영문 kebab 변환 가능한 동사구>
- 의도: <왜 지금 이 작업인가 — 해결하려는 문제/동기 1~2문장>
- 맥락: <도메인 용어·전제 배경, 없으면 생략>

## 통과 기준
- [ ] <사용자가 관찰 가능한 동작 서술 — 검증 가능한 문장>
- [ ] ...

## 제외 범위
- <이번에 하지 않는 것>

## 테스트 범위
- 수준·대상: <unit/integration + 동작 수준 대상> (면제 시: 면제 — 사유 1줄)

## 미확정 사항
- [explore 위임] <코드를 보면 답이 나오는 질문>
- [explore 후 조건부] <탐색 결과 X면 사용자에게 Y를 묻는다>
(없으면 섹션 생략)

## 참조 컨텍스트 문서   (docs/ 참조가 있었을 때만)
- <파일 목록>
```

### 작성 규칙

- **요약 '작업' 행**: 브랜치 slug 원천이므로 영문 kebab-case 변환 가능한 동사구로 작성한다 (기존 첫 bullet 규약 승계).
- **요약 '의도' 행**: evaluator의 "의도 누락" 판정 축과 planner 설계 선택의 근거가 되는 문서다 — 비우지 않는다.
- **통과 기준**: 사용자가 관찰 가능한 동작 서술만 적는다. 테스트 명령어·파일 경로 금지 (명령 확정은 plan `## 테스트 실행`의 몫). "통과 기준"은 clarify → plan(태스크별 통과 기준) → evaluator(plan 부합 검증)가 같은 이름으로 연결되는 체인이므로 개명하지 않는다.
- **테스트 범위**: ④에서 협의한 수준·대상 한 줄. 면제 사이클이면 `면제 — <사유>`.
- **미확정 사항**: 무조건부 사용자 질문은 인터뷰 중 소진이 원칙이다. 여기 남길 수 있는 것은 `[explore 위임]`(코드를 보면 답이 나오는 것)과 `[explore 후 조건부]`(탐색 결과에 따라 사용자에게 물을 것) 두 태그뿐이다 — 메인의 "explore 후 ② 전 자유 질문" 트리거로 쓰인다. `[explore 후 조건부]`의 조건은 코드 존재 여부로 판정 가능한 술어로 쓴다 (예: "△△ 심볼/디렉터리가 존재하면 사용자에게 재사용 여부를 묻는다"). "~한 구조라면" 같은 해석 여지가 있는 술어는 explorer마다 판정이 갈린다 — explorer가 `## 미확정 사항 회신`의 [조건 보고]에서 성립/불성립/판정불가로 회신할 수 있어야 한다. 남길 게 없으면 섹션째 생략.
- **참조 컨텍스트 문서**: ⓪에서 읽은 문서가 있을 때만 이 섹션을 둔다. 헤더명 고정 — context-doc-updater 호출부가 이 이름을 직접 참조하므로 개명·삭제하지 않는다. docs/ 부재면 섹션째 생략.
- **게이트 ① confirm 절차**: 요약(의도 포함) → 통과 기준 → 제외 범위 → 테스트 범위 → 미확정 사항 → 참조 컨텍스트 문서 순으로 전체 출력한 뒤 `AskUserQuestion`으로 confirm한다.

### Confirm 발화

> 이 정리가 의도와 일치합니까? `확인` 또는 `수정 필요 (어떤 부분)` 형식으로 답해주세요.

확인을 받기 전에는 explore로 진입하지 않는다.

## ③ Socratic Challenge

Understanding Lock 확정 직후 무조건 1회 실행한다.

명확해 보이는 안일수록 숨은 가정이 위험하다. 사용자가 "다 정리됐다"고 느낄 때 도전을 거치지 않으면 잘못된 가정이 explore/plan을 통째로 망친다.

### 진행

1. 확정된 이해의 핵심 가정 2~3개를 식별
2. 각각에 정면 도전:
   > 이 접근은 X 측면에서 약점이 있는데, 어떻게 반박하시겠습니까?
3. 사용자 답변에 따라:
   - 합리적 반박 → accept, 다음 가정으로
   - 약한 반박 → escalate: *"그 반박은 Y를 가정하는데, Y가 보장됩니까?"*
4. 진짜 빈틈이 드러나면 ②로 돌아가 lock을 갱신

> 가정 2~3개 모두 처리하면 종료. escalate는 가정당 최대 1회. lock 갱신은 1회까지만 (핑퐁 방지).

### 종료 발화

> 가정 점검을 마쳤습니다. explore로 넘어갑니다.

## ④ 테스트 수준·대상 (협의)

**코드 변경 작업은 테스트 작성이 전제다** — generate 단계에서 generator가 태스크 안에서 *테스트 작성 → RED 확인 → 구현 → GREEN 확인*(TDD)으로 진행하므로, "작성할지"는 묻지 않는다. clarify가 협의하는 것은 **수준과 대상**뿐이다.

- **면제는 작업 성격으로만**: 순수 문서·설정 변경처럼 테스트가 명백히 무의미한 작업만 가볍게 면제 합의 — 깊이 캐묻지 않는다 (속도가 task-pipeline의 가치)
- **순수 리팩토링**: 변경 대상을 커버하는 기존 테스트가 있으면 그 회귀로 갈음 가능. 커버가 없거나 불확실하면 *특성화 테스트(현재 동작을 고정하는 테스트) 선행*을 선택지로 제시해 협의

### 협의 질문 예시

> 테스트는 어느 수준으로 할까요?
> - A. 단위 테스트 (태스크별 동작 검증)
> - B. 단위 + 통합 테스트
> - C. (리팩토링) 특성화 테스트 선행
> - D. (docs·설정 작업) 테스트 면제 (사유 기록)

clarify는 *실현 가능성*(테스트 러너·기존 커버리지)을 모른다 — 여기서 정하는 건 **의도·타겟**이다. 러너·실행 명령은 explore가 진단하고 plan이 확정한다.

### 확정 결과 기록

협의로 정해진 결과를 산출물 `## 테스트 범위` 섹션에 `- 수준·대상:` 한 줄로 기록한다 — 수준(단위/통합/E2E/특성화)과 검증할 동작 수준의 대상을 함께 적는다. 테스트 면제 사이클이면 `면제 — <사유>`(예: "순수 docs 변경")로 대체한다. 러너·실행 명령 같은 사실 보정은 explore·plan의 몫이므로 여기 적지 않는다.

## clarify 산출물

산출물 `01-clarify.md` 본문은 ②의 *정리 형식* 그대로다 — 요약 / 통과 기준 / 제외 범위 / 테스트 범위 / 미확정 사항(있을 때만) / 참조 컨텍스트 문서(docs/ 참조가 있었을 때만)의 고정 4섹션 + 조건부 2섹션(미확정 사항 · 참조 컨텍스트 문서). 이 본문을 컨텍스트에 보유한 채 explore로 진입한다.

이 산출물은 explorer 호출 prompt에 본문 통째로 명시 주입한다. explorer는 `## 테스트 환경` 진단으로 테스트 범위의 의도를 사실(러너·실행 명령·커버리지)로 보정하고, plan이 태스크별 통과 기준·테스트 계약·실행 명령으로 확정한다. 미확정 사항은 메인이 explore 전후(② 게이트 전) 자유 질문으로 처리한다.
