# task-pipeline clarify — 인터뷰 기법

clarify는 brainstorming 스킬의 핵심 3개 개념을 *내장*해 직접 수행한다. 스킬을 호출하는 게 아니라 그 기법을 메인이 적용한다.

## ① One question at a time

한 번에 한 질문만, 다지선다 우선.

여러 질문을 묶으면 사용자가 일부만 답하거나 답이 모호해진다. 다지선다는 답변 부담을 줄이고 응답을 명확하게 만든다.

### 좋은 예
> 이 작업의 통과 기준은 어느 쪽에 가깝나요?
> - A. 테스트 추가 + `pnpm test` 통과
> - B. 기존 테스트가 깨지지 않으면 OK
> - C. 빌드만 통과하면 OK
> - D. 그 외 (직접 설명)

### 나쁜 예
> 이 작업의 목적은 뭐고, 어떤 파일을 건드릴 것 같고, 통과 기준은 무엇이고, 위험은 뭐죠?

답변에 깊이가 필요한 부분(예: 의도가 모호)은 개방형 질문으로 변경. 기본은 다지선다.

## ② Understanding Lock

### clarify 종료 조건

다음 4가지가 모두 명확해질 때까지 인터뷰를 계속한다. 미만에서 끝내면 explore/plan/evaluate가 흔들린다.

1. **목적** — 무엇을 왜 만드는가
2. **통과 기준 (verify)** — 어떤 명령으로 통과를 확인할 것인가. 정말 없으면 *"verify 불가"* 임을 사용자와 합의
3. **non-goals** — 무엇을 하지 *않을* 것인가
4. **테스트 범위** — 이 작업에 테스트를 작성할지·어느 수준까지 할지. 아래 ④ 참고

넷 다 채워지면 Lock으로 넘어간다.

### Lock 진행

명시 정리를 보여주고 사용자 confirm을 받는다. 흐릿하게 explore로 넘어가면 잘못된 전제 위에 후속 단계가 쌓인다.

### 정리 형식

```markdown
## Understanding Summary
- 무엇을 만드나 (5~7 bullets)
- 왜 (목적/배경)
- 누구를 위한
- 핵심 제약
- explicit non-goals

## Assumptions
- 명시되지 않았지만 가정한 것 1~N개

## Open Questions
- 미해결 질문 (있을 때만)
```

### Confirm 발화

> 이 정리가 의도와 일치합니까? `확인` 또는 `수정 필요 (어떤 부분)` 형식으로 답해주세요.

확인을 받기 전에는 explore로 진입하지 않는다.

## ③ Socratic Challenge

Understanding Lock 확정 직후 무조건 1회 실행한다.

명확해 보이는 안일수록 숨은 가정이 위험하다. 사용자가 "다 정리됐다"고 느낄 때 도전을 거치지 않으면 잘못된 가정이 explore/plan을 통째로 망친다.

### 진행

1. 확정된 이해의 핵심 가정 2~3개를 식별
2. 각각에 정면 도전:
   > 이 접근은 X 측면에서 약점이 있는데, 어떻게 반박하시겠습니까?
3. 사용자 답변에 따라:
   - 합리적 반박 → accept, 다음 가정으로
   - 약한 반박 → escalate: *"그 반박은 Y를 가정하는데, Y가 보장됩니까?"*
4. 진짜 빈틈이 드러나면 ②로 돌아가 lock을 갱신

> 가정 2~3개 모두 처리하면 종료. escalate는 가정당 최대 1회. lock 갱신은 1회까지만 (핑퐁 방지).

### 종료 발화

> 가정 점검을 마쳤습니다. explore로 넘어갑니다.

## ④ 테스트 범위 (제안 → 협의)

clarify는 테스트를 *강제*하지 않는다. 대신 **작업 범위·성격을 보고 테스트 여부와 수준을 능동 제안**하고, 사용자와 협의해 확정한다. 여기서 확정된 결과만 이후 단계(plan/evaluate)가 강제한다 — clarify는 *결정의 장*, 강제는 *합의된 범위에만*.

### 제안 기준

작업 성격을 보고 기본 제안을 만든다 (사용자가 바꿀 수 있음):

| 작업 성격 | 기본 제안 |
|---|---|
| 신규 동작·기능 추가 | 핵심 동작에 대한 단위/통합 테스트 작성 권장 |
| 버그 수정 | 실패를 재현하는 회귀 테스트 권장 |
| 순수 리팩토링 (동작 보존) | 기존 테스트 회귀 통과로 갈음, 신규 작성 불필요 제안 |
| 순수 문서·설정 변경 | 테스트 불필요 제안 (가볍게 면제 합의) |

> 테스트가 명백히 무의미한 성격(docs·단순 설정)이면 깊이 캐묻지 않는다 — 속도가 task-pipeline의 가치다.

### 협의 질문 예시

> 이 작업의 테스트는 어떻게 할까요?
> - A. 단위 테스트 추가
> - B. 통합/E2E 테스트 추가
> - C. 기존 테스트 회귀 통과만 (신규 작성 없음)
> - D. 테스트 불필요 (사유 기록)

clarify는 *실현 가능성*(테스트 러너·기존 커버리지)을 모른다 — 여기서 정하는 건 **의도·타겟**이다. 실제 명령·실현 가능성은 explore가 보정하고 plan이 태스크로 확정한다.

### 확정 결과 기록

협의로 정해진 결과를 산출물 `## 테스트 범위` 섹션에 기록한다:

- **작성**: `O` (작성함) / `X` (면제) — 면제면 사유를 함께
- **수준·종류**: 단위 / 통합 / E2E / 스모크 중 (의도)
- **커버 대상·제외**: 무엇을 검증하길 원하나 / test non-goals
- **verify 명령 후보**: 통과 기준의 테스트 실행 명령 후보 (explore가 보정)

## clarify 산출물

다음을 컨텍스트에 보유한 채 explore로 진입한다:

- Understanding Summary
- Assumptions
- Challenge 통과한 핵심 전제
- Verify 단서
- `## 테스트 범위` (④에서 협의 확정한 작성 여부·수준·대상·verify 후보)

이 산출물은 explorer 호출 prompt에 명시 주입한다. explorer는 `## 테스트 범위`의 *의도*를 코드로 보정(러너·기존 커버리지 확인)하고, plan이 테스트 태스크로 확정한다.
