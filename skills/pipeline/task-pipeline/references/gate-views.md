# 게이트 뷰 — 사람 접점 발화 규격

사람 개입 5접점(수렴 brief 확인 · ① 착수 승인 · blocked 알림 · ③ 최종 점검 · handoff 제시)의 화면 출력 규격. 정본(brief·plan·state)은 에이전트 인계 정밀성을 위해 밀도를 유지하고, 사람에게는 메인이 이 규격대로 뷰를 **즉석 생성**해 제시한다. 뷰는 저장하지 않는다 — 표현 계층이며, 판정 귀속은 lock의 sha(정본)가 담당. 존재 이유: 판정 비용이 높으면 게이트는 "일단 됐다고 하자"로 퇴화한다 — 뷰의 목표는 **훑고 고를 수 있는 판정 재료**.

## 공통 원칙
- **제목이 곧 요청** — 첫 줄에서 지금 내릴 판정이 보인다.
- **판정에 필요한 것만** — 커밋 해시·로그 경로 같은 참고 정보는 원문 경로로 밀어낸다.
- **정본에 없는 말 금지** — 뷰의 모든 문장은 brief·plan·state·journal·verify에서 유도 가능해야 한다. 뷰↔정본이 다르면 정본이 정답.
- **원문 경로 병기** — 뷰 말미에 상세 원문 경로 한 줄.
- **라벨은 짧은 명사구** — 문장형·풀어쓴 설명형 라벨 금지. 설명은 라벨이 아니라 내용에.
- **화면 라벨 통일** — 아래 표. ID(G-/C-/N-/A-/Q-/S-/H-)는 앵커로 유지.
- 발화는 `AskUserQuestion` 다지선다(header 12자 이내, 권장안 `(권장)`), 판정 하나에 문답 하나.

## 화면 라벨
| 내부 용어 | 화면 |
|---|---|
| ① 착수 게이트 · ③ 검수 | 착수 승인 · 최종 점검 |
| 걸음 · 웨이브 | 단계 · (미표기 — 순서·병렬만 표시) |
| 최종 검증 · 라운드 상한 | 자동 검증 · 재시도 한도 |
| brief · plan · lock · 체크리스트 · 이월 · handoff · blocked | 그대로 사용 |

## 접점 1 — 수렴 brief 확인 (매듭)
채워진 섹션을 항목당 한 줄로 제시. 화법·순서는 `clarify-method.md`.

```
## brief 확인 — <섹션명>
- <ID> · <한 줄>
[맞음 / 빠진 것 있음 / 뺄 것 있음]
```

## 접점 2 — 착수 승인 (①)
brief는 수렴에서 매듭별로 확인됐다 — 뷰의 무게중심은 ①에서 처음 등장하는 plan 요소(단계·자동 검증·체크리스트·재시도 한도). 체크리스트는 ③ 퇴화를 막는 뿌리 — 반드시 노출하고 "최종 점검 때 다시 제시"를 예고한다.

```
## 착수 승인
**목표**: <한 줄 — 수렴 합의 그대로>
**단계** (N): S-n · <한 줄씩, 의존·병렬은 순서·괄호로>
**자동 검증**: <verify_cmd> · 재시도 한도 N회
**체크리스트** (최종 점검 때 다시 제시): <항목 한 줄 — 확인 수단>
**전제**: <A- 한 줄> / **제외**: <N- 한 줄>
원문: brief.md · plan.md
→ 승인 시 계획 고정(lock) · [승인 / 수정 / 중단]
```

예시:

```
## 착수 승인
**목표**: 보고자·담당자 소스를 파싱 API → 로시안으로 변경
**단계** (4):
1. S-1 · DB에 보고자 컬럼 추가
2. S-2 · 로시안 registeredBy 파싱 — 누락 시 빈 값
3. S-3 · 큐 적재 시 운반 + 계정 매칭
4. S-4 · 저장 시 보고자/담당자 각각 기입 (3과 순서 무관)
**자동 검증**: pnpm test && pnpm build · 재시도 한도 4회
**체크리스트** (최종 점검 때 다시 제시):
1. problem_hint 쓰기가 한 곳뿐인지 — grep
2. 검수결과 필터 무변경 — diff
**전제**: 로시안이 registeredBy 제공 · 누락 시 빈 값(합의됨)
**제외**: PRD 데이터 이관 · admin 보고자 입력
원문: brief.md · plan.md
→ 승인 시 계획 고정(lock) · [승인 / 수정 / 중단]
```

## 접점 3 — blocked 알림
```
## blocked — <S-n> 진행 막힘
**막힌 것**: <원인 한 줄 — 충돌 지점 ID 인라인>
**영향**: <대기 단계 · 검증 영향>
[<권장안> (권장) / <대안> / brief 재수렴]
```

## 접점 4 — 최종 점검 (③)
순서 고정: **요약 → 체크리스트 문답 ×N → 이월 후보 → report 전문 → 종합 판정**. 항목별 판정은 journal `문답`으로 기록.

1. **요약** (3줄 이내): 단계·커밋·자동 검증 결과 + "체크리스트 N건 확인" 예고.
2. **체크리스트 문답** — 항목당 1문답. 확인 방법(how, lock 때 동결)을 메인이 **실제 실행해 증거를 첨부**한다 — 실행은 심부름, 판정은 사람. 증거 없이 항목을 넘기지 않는다. `원본 확인` 선택 시 raw 출력을 제시하고 같은 항목을 재문답.

```
[체크리스트 k/N] <항목 한 줄> (<ID>)
확인 방법(lock 때 합의): <how>
증거(방금 실행): <결과 요약 + ✓/✗>
[OK / 미달 → 수정 / 원본 확인]
```

3. **이월 후보**: 체크리스트 밖 발견 → handoff 등록 제안(출처 참조 포함).
4. **report 전문**: `core.sh report` 뷰 전문을 응답 본문에 그대로(요약·발췌 금지) — 서명 직전 최종 서류, "점검 때 본 것 = 기록".
5. **종합 판정**: [수용 / 수정 반송 / 수용+이월].

예시(문답 1건):

```
[체크리스트 1/2] problem_hint 쓰기가 한 곳뿐인지 (C-1)
확인 방법(lock 때 합의): fetch/enqueue가 problem_hint를 직접 쓰지 않는지 grep
증거(방금 실행): write는 batch-parse.ts의 completeParseAndPromote 트랜잭션 1곳뿐 · fetch/enqueue 매치 0건 ✓
[OK / 미달 → 수정 / 원본 확인]
```

## 접점 5 — handoff 제시 (발동·resume)
```
## handoff — 이전 사이클 이월 N건
- H-n · <한 줄> — <이번 요청과의 관련>
[<관련 항목> 채택 / 모두 채택 / 이번엔 안 함]
```
채택 시 `handoff consume --by` + brief 재료로.
