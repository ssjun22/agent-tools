# plan 규칙 — 기준 설계 + 분해

planner는 두 가지를 한다: **기준 설계**(성공 요소를 판정 수단에 배분) → **분해**(걸음·완료 조건·의존 그래프). 산출은 `templates/plan.md` 골격.

## 1. 기준 설계
brief의 모든 `G-`(성공)·`C-`(보존)를 **verify(기계 판정) 또는 검수 체크리스트(사람 판정)** 중 하나에 배정한다 — 배정 없는 기준은 없다.
- **verify로**: 명령 exit로 판정 가능한 것 → `json steps`의 `check`(걸음) 또는 lock의 `verify_cmd`(최종).
- **검수로**: 사람만 판정 가능한 것(UI 렌더·톤·의도 부합) → `human_check`, ③ 검수 체크리스트로. 확인 방법(어디를 열어 무엇을 본다)을 함께 적어 ① lock의 `--check "항목 :: 방법"`으로 승격한다.
- **게으른 경로 검사**: "이 기준이 하드코딩·스텁으로 통과해 버릴 여지가 있는가"를 배정 시점에 점검하고, 있으면 그 빈틈을 닫는 check를 추가하거나 검수로 올린다.
- **실패 먼저 보기**: 기존 수단으로 실패를 목격할 수 없는 기준은 걸음에 "실패 먼저 볼 것"을 표기 — 루프에서 테스트 작성→실패→구현→통과로 간다.

## 2. 유형(type)
`feat`/`fix`/`refactor`/`chore`/`docs`/`test` 중 하나(frontmatter). 브랜치 `<type>/<slug>` prefix + 걸음 커밋 subject의 기본 type.

## 3. 분해 — 걸음 자르기
①통과 상태(걸음 끝 = 커밋 지점)에서 자른다. 한 걸음은 다음 단위로서 모두 의미를 가져야 한다: 롤백 단위 · 재시도 식별 단위 · 검증 단위 · 리뷰 단위. **양이 작아서가 아니라 단위로 못 서서 합친다.**

분해 기준: ①한 걸음 한 종류 ②한 호흡 크기 ③하한(합침 검사·고유 확인 검사) ④앞 걸음의 통과를 뒷 걸음이 안 깨는 배열 ⑤같은 웨이브는 `files` 소유권 서로소(겹치면 순차 강등이 아니라 재분해).

유형별 1차 휴리스틱: `feat`=vertical slice(크면 계약 우선: stage1 계약 동결 → stage2 소비) · `refactor`=의미 단위(같은 컨셉은 흩어져도 한 덩어리) · `chore 마이그레이션`=의존 순서 · `docs`=섹션 단위.

## 4. 걸음별 판정 수단
코드 변경 걸음은 판정 수단 확보가 구현에 선행한다. 각 걸음에 `check`(걸음 확인 명령) 또는 `human_check` 최소 하나. 테스트는 별도 걸음이 아니라 걸음 안에서(실패 먼저 보기 → 통과). 기존 커버로 갈음 가능하면 근거를 산문에 적는다.

## 5. 의존 그래프 · 웨이브
`depends_on`으로 순서를 표현. 웨이브는 `wave(S)=1+max(wave(deps))`로 파생(명기·기록하지 않음). 같은 웨이브 걸음은 `files` 서로소여야 병렬(워크트리 분기) 가능. 의존이 없는데 순서를 강제하면 산문에 "순서 강제: 사유" 한 줄.

## 6. 상한(max_rounds)
최종 검증 **FAIL 누적**의 회로 차단기(PASS·ERROR는 상한을 소모하지 않는다) — 소진은 '코드가 아직 안 됨'이 아니라 'plan이 틀렸을 확률이 높음' 신호(③ 아닌 사람 개입 이벤트). 규모별 권장: 단일 단순 2 / 2~4걸음 3 / 5+·외부의존 4 / verify 불가 2. 사용자가 ①에서 변경 가능.

## 산문 vs JSON 역할 분담
산문 = 서사(왜 이렇게 자르나), `json steps` = 기계 정본(래퍼·generator 배정은 블록만 읽음). 이중 작성 금지 — 겹침은 id·제목뿐. `files`는 write 소유 순수 경로만. 걸음당 확인 수단 ≥1은 ① lock에서 래퍼가 검증(`STEP_NO_CHECK`).
