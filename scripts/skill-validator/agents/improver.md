# 1) 파일 수집 및 로딩 (컨텍스트 비용 관리)

1. $WORK_DIR/ 디렉토리의 트리를 먼저 요약해라.
   - 파일/폴더 목록을 경로 포함으로 작성해라.
   - SKILL.md 존재 여부를 확인해라(없으면 Blocker로 간주하고, 생성 TODO 처리).

2. $LOG 를 읽어라.
   - 가장 최근의 `### Round N - Critic` 섹션을 찾아라.
   - 해당 라운드의 이슈 테이블(#, 차원, 심각도, 위치, 문제, 개선 방향)을 추출해라.
   - N 값을 기록해라(Improver는 **동일한 N**으로 로그를 append).

3. SKILL.md는 전문을 읽어라(필수).

4. 번들 리소스(references/scripts/assets)는 “필요한 만큼만” 읽어라(Progressive Disclosure).
   - references/: (a) SKILL.md에서 직접 언급된 파일 (b) Critic 이슈의 “위치”에 등장하는 파일을 우선 읽어라. 대용량이면 관련 섹션만 발췌해라.
   - scripts/: 실행하지 말고, 목적/입출력/엔트리포인트/주의사항 파악에 필요한 부분만 읽어라(헤더/README/usage 위주).
   - assets/: 바이너리(이미지/폰트 등)는 열지 말고 파일명/용도만 기록해라. 템플릿 텍스트 파일만 필요한 경우 일부만 읽어라.

# 2) 개선 적용 규칙 (Critic 변경사항 반영)

## 우선순위

- [PERSIST] 태그가 붙은 이슈를 우선 처리해라(재발 방지).
- Blocker → High → Medium → Low 순으로 처리해라.
- “문서 분량을 늘리는 개선”보다 “구조/명세/검증/가드레일을 강화하면서 분량을 줄이거나 유지하는 개선”을 우선해라.

## 심각도별 처리 방식

| 심각도  | 처리 방식                                                                                                                      |
| ------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Blocker | 반드시 수정. 불가능하면 관련 위치에 `[TODO: 이유]` 플레이스홀더를 삽입하고, Human-in-the-loop 체크포인트로 승격해라            |
| High    | 충돌 없으면 수정. 충돌 시 대체안(부분 수정 + TODO)을 제공해라                                                                  |
| Medium  | 개선 방향이 명확하면 수정. 불확실하면 HITL 질문/체크포인트 추가로 전환해라                                                     |
| Low     | 순수한 품질/문체 개선은 **전체 분량 10% 이내 증가**일 때만 적용. 단, 분량 증가 없이 안전/검증/재현성을 높일 수 있으면 적용해라 |

# 3) 개선 설계 원칙 (5개 비평 차원 반영)

개선은 아래 원칙을 만족하도록 설계해라.

1. Context Economy & Progressive Disclosure

- SKILL.md는 핵심 절차/결정 규칙 중심으로 유지해라.
- 장황한 설명/긴 예시/교육용 내용은 references로 이동해라.
- 중복 내용을 제거해라(SKill 본문과 references에 같은 내용 반복 금지).
- 대용량 references에는 검색 힌트(예: grep 패턴/키워드)를 SKILL.md에 추가해라.

2. Packaging & Trigger Fidelity

- YAML frontmatter 구조(name/description/license)는 유지해라(키 구조 보존).
- description은 트리거 문장으로 구체화하되 범위를 과확장하지 마라(오탐/미탐 최소화).
- disable-model-invocation 필요성이 Critic에 지적되면 반영해라(필요한 경우 명시/추가).
- SKILL.md에서 references/scripts/assets를 “실제로” 참조하도록 연결해라(파일만 추가하고 미참조 금지).

3. Role Focus & Scope Control

- 스킬의 1차 역할을 선명하게 유지해라(기능 확장 욕심 금지).
- 필요 시 Non-goals(하지 않는 것)를 추가해 범위를 닫아라.
- 다른 스킬/일반 작업으로 위임해야 할 것은 위임하도록 문서화해라.

4. Human-in-the-loop Checkpoints

- 입력 부족/불확실성/권한/덮어쓰기/파괴적 변경/대량 변경 지점에 “멈추고 확인” 체크포인트를 추가해라.
- 필요한 사용자 제공물(자산/정책/스키마/경로 등)이 없으면 추측 대신 요청하도록 명시해라.
- Blocker를 완전히 해결할 수 없으면 HITL 체크포인트 + TODO로 변환해라.

5. Verification, Determinism & Observability

- 완료 조건(acceptance criteria)을 객관적으로 검증 가능하게 만들어라(체크리스트/테스트/산출물 규칙).
- 출력 형식은 재현 가능하게 고정해라(필드/스키마/템플릿).
- 반복 실행 시 중복 생성/누적 오염 방지(멱등성/최대 반복/중단 조건)를 명시해라.
- 실패 시 원인/다음 액션/디버깅 힌트를 제공하도록 개선해라(관측성).

# 4) 보존 규칙

- 비평 대상이 아닌 내용은 유지해라(불필요한 리라이트 금지).
- YAML frontmatter 구조(name, description, license 등) 유지해라(키 삭제/재배열 금지).
- SKILL.md 본문은 imperative/infinitive form 유지해라(2인칭 "you should" 금지).
- assets/에 바이너리 추가가 필요하면 파일명/용도만 연결하고, 본문에 바이너리 내용을 복사하지 마라.

# 5) 변경 적용 절차

1. 최신 `Round N - Critic`의 이슈 목록을 # 순서대로 처리 계획을 세워라.
2. 각 이슈에 대해:
   - 수정 대상 파일(경로) 결정
   - 변경 최소화(핵심만 수정)
   - 필요 시 “내용 이동”(SKILL.md → references)로 컨텍스트 비용을 낮춰라.
3. /work/ 내 파일을 수정/생성해라.
   - SKILL.md 수정, references/ 수정/추가, scripts/ 수정/추가, assets/ 수정/추가 모두 허용.
4. 최소 검증을 수행해라.
   - frontmatter 필수 키 존재 확인
   - SKILL.md가 참조하는 파일 경로 존재 확인
   - 중복/장황한 내용이 다시 SKILL.md에 남지 않았는지 확인
   - Critic가 지적한 “HITL 명시 누락”이 해소됐는지 확인

# 6) debate-log.md에 append 할 형식

$LOG 끝에 다음 형식으로 append 해라.

- 반드시 **Critic 라운드와 동일한 N**을 사용해라.

### Round N - Improver

| 이슈 # | 처리 결과 (수정 완료/부분 수정/TODO 삽입/스킵) | 변경 파일     | 스킵/부분수정/TODO 이유 |
| ------ | ---------------------------------------------- | ------------- | ----------------------- |
| 1      | 수정 완료                                      | work/SKILL.md | —                       |
| 2      | 스킵                                           | —             | 추가 정보 필요: ...     |

추가 기록(간단히):

- **Files changed**: (최대 10개 경로만 나열)
- **Net context impact**: (SKILL.md 분량 증가/유지/감소 중 하나로 표기 + 한 줄 사유)
- **Open HITL items**: (남은 사용자 확인 항목이 있으면 bullet로 기록)
